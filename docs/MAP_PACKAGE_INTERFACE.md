# AGT Mapping / Navigation Map Package Interface

Status: v1, implementation contract for the mapping-to-navigation boundary.

> 2026-09-24 update: the mapping_source contract below remains valid for raw PGO exports. For the complete navigation candidate, human acceptance and registry/latest_validated publication workflow, see [the integration report](mcp-traversability-main-integration.md). The shared installed map-manager CLI packages mapping-generated navigation assets; it does not regenerate them.

## Ownership

`agt_mapping_framework` owns FAST-LIO2, PGO, map saving, keyframe patches and
the publication of a validated mapping package. `agt_navigation_v3` is a
consumer: it validates the package, generates navigation derivatives (for
example the Nav2 PGM/YAML map), and starts localization and Nav2.

Neither side changes the FAST-LIO2 or PGO algorithm parameters as part of this
interface.

| Frontend topic | `/mapping/frontend/odometry`, `/mapping/frontend/cloud`, `/mapping/frontend/path` | Not consumed after export |

| Files | `map.pcd`, `poses.txt`, `poses_timed.txt`, `patches/`, `calibration.yaml` | Reads package; creates Nav2 derivatives in its runtime package |

## TF and pose contract

* Mapping poses in `poses.txt` and `poses_timed.txt` are `T_map_body`.
* Keyframe patch point clouds are in the body frame (`body`), not an implicit
  sensor frame.
* The mapping package does not publish navigation runtime TF.
* Navigation continues to own and publish `map -> odom` for localization and
  `odom -> base_link` for the robot state. These are not baked into the PGO
  files.
* The mapping package uses the stable names `map`, `body`, and `lidar`; a
  deployment may remap the robot body to `base_link` at the navigation edge.

## Package layout

Published by the mapping repository at `AGT_MAP_ROOT/<site>/<version>`:

```text
<site>/<version>/
├── manifest.yaml
├── metadata.yaml
├── map.pcd
├── poses.txt
├── poses_timed.txt
├── patches/
├── calibration.yaml
├── relocalization/              # optional, generated by mapping workflow
└── checksums.sha256
```

`manifest.yaml` declares `schema_version: 1`, `package_kind: mapping_source`,
the required files, and SHA-256 values. Navigation must reject a missing file,
checksum mismatch, non-PGO backend, or non-optimized package before starting
localization/Nav2.

`poses.txt` retains the existing line format:

```text
patch_name x y z qw qx qy qz
```

The exporter is atomic and never overwrites an existing `<site>/<version>`.
Use `export_map_package --source-dir ... --site ... --version ...`; `--map-root`
defaults to `AGT_MAP_ROOT` and then `~/ros2_ws/maps`.

## Navigation conversion boundary

The navigation repository may convert `map.pcd` and the PGO trajectory into a
versioned Nav2 package. That derived package is a consumer artifact and must
retain provenance pointing to the source package and its checksum. The source
PGO package remains immutable and is the input for global relocalization.

## Validation sequence

```text
mapping export -> manifest/checksum validation -> PCD/Nav2 conversion
                -> relocalization asset load -> global localization
                -> map->odom + odom->base_link -> Nav2
```

The offline bag `bunker_mid360_mapping_20260901_211105` is the acceptance
fixture. Mapping export must be completed before navigation conversion; a
navigation launch must not silently fall back to a raw PCD or an unoptimized
frontend artifact.
